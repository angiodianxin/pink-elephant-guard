# 媒体別要件

`SKILL.md` から必要時にだけ読む参照資料（progressive disclosure、`design-claude.md` §13.1）。
正本は `design-claude.md` §10 で、本ファイルはそれを L3 の作業手順へ展開したものである。
工程2（Clean Brief）で媒体を確定した時点で、該当する節だけを読む。

各節は次の 4 項目で構成する。

| 項目 | 内容 |
|---|---|
| 面と `surface` | manifest の `surface` に宣言し、初稿の面ラベルに使う値の例 |
| Clean Brief と生成 | 工程2・工程3 で守る記述上の要件 |
| 検査で見る箇所 | 工程4a（L1）・工程4b（L2）・L3 の最終確認で見落としやすい箇所 |
| 検査済みと報告できる範囲 | 工程4 の結果を報告するとき、「検査済み」と言える範囲と言えない範囲 |

## 共通原則

- **検査済みと報告できるのは、L1・L2 が実際に読んだテキストだけである。** PASS 判定は L1・L2 の結果からのみ導き、L3 の自己評価で代替しない（§11）。L2 の出力 `applied_checks` に含まれない検査は、実施していない。
- 受け手が見る面は、文字として書かれていないものも含めて `SURFACE` に数える。画像内文字、ラベル、音、最終フレーム、プレースホルダーは、いずれも受け手に届く面である。
- 却下物を「出さないもの」として再列挙しない。negative prompt、「起こらない出来事」、無効ラベル、「廃止しました」の告知は、いずれも却下物を完成面へ戻す経路である。現在必要なものだけを肯定形で書く。
- 実物（実画像、実動画、実音声、実行中の UI）を確認していない範囲は、報告で「未確認」と明示する。テキストの検査結果を実物の検査結果として書かない。

報告の書き分けの例:

~~~text
検査済み: プロンプト文面（L1 PASS、L2 PASS: semantic / rationale / visual）
未確認:   生成された実画像の画素、画像内に描画された文字
~~~

## 1. 文章

広告コピー、SNS 投稿、記事、見出し、CTA、台詞、ナレーション、字幕、配布用の要約や資料。

### 面と `surface`

`headline`、`lead`、`body`、`cta`、`footnote`、`caption`、`subtitle` など。
見出し・冒頭・CTA・結論にあたる面を宣言しておくと、L2 の Attention leak 検査がその面を主題の検査対象として扱える。

### Clean Brief と生成

- 現在状態を主語にして最初から組み直す。修正前の文章から数語を削る方式をとらない。
- 削除で生じた空白は、目的に合う内容と情報階層で埋める。「現在はありません」「廃止しました」など、**不在の説明を安易に置かない。** 不在自体を訴求するかは工程1 で確定し、訴求する場合だけ `visible_exceptions` として保持する。
- ユーザーが差分報告を求めていない限り、変更経緯（「以前は」「に代わり」「今後は」）を完成稿へ出さない。変更告知そのものが現在状態である場合（営業時間の変更など）は例外で、`target_state` に含めておく。

### 検査で見る箇所

- **見出し、冒頭、本文、CTA、脚注まで**を検査する。脚注、注記、キャプション、ハッシュタグ、alt テキストは見落としやすい。
- 却下要素の不在や比較が、見出し・冒頭・CTA・結論の主題になっていないか（Attention leak）。
- 本文全体が「〜はありません」調に傾いていないか。L1・L2 を通っても、完成物として自然に成立しているかの最終判断は L3 の責務である（§12.5）。

### 検査済みと報告できる範囲

- L1・L2 へ渡した初稿ファイルの全文。面ラベルを付けた面については Attention leak も含む。
- 面ラベルを付けなかった初稿では、L2 は Attention leak を実施しない。この場合、主題の偏りを検査済みと報告しない。
- 初稿を組版・投稿先へ流し込んだ後の表示（改行位置、切り詰め、プレビューカード）は未確認である。

## 2. 画像生成プロンプト

画像生成モデルへ渡すプロンプト、およびそこで指定する画像内文字・ラベル・背景小物。

### 面と `surface`

`image_prompt` を含める。画像内の文字を指定する場合は `image_text` などの面を分けて宣言してもよい。
`surface` に `image_prompt`、`visual`、`storyboard` のいずれかが含まれるか、初稿が生成プロンプトの体裁であれば、L2 は Visual leak 検査を適用する。

### Clean Brief と生成

- 現在必要な**被写体、形、配置、素材、光、接触関係**を肯定形で記述する。「何が、どこに、何と接して、どう照らされているか」を書けば、削除物の居場所は残らない。
- **却下物を長い negative prompt として再列挙しない。** negative prompt は却下物の名を生成器へ再投入する経路であり、Literal leak そのものである。削除後の空白は、代わりに置く被写体や構図で埋める。
- 削除物の容器、皿、持ち手、包装、値札、空席、「何も置かれていない台」だけが残る構図を書かない。

### 検査で見る箇所

- 表示文字、ラベル、看板、値札、パッケージ、背景小物の指定に旧案が残っていないか。
- 削除物の輪郭、破片、影、反射、プレースホルダー（「かつて置かれていた跡」）を示す記述がないか（Visual leak）。
- スタイル指定や参照画像の説明が旧案の構図を前提にしていないか。

### 検査済みと報告できる範囲

- 検査済みと言えるのは**プロンプト文面**だけである。L2 の `applied_checks` に `visual` が含まれていても、それはプロンプト文面上の視覚残留の検査を意味する。
- **実画像を確認していない場合、画素上の残留（描画された文字、輪郭、影、背景小物）を検査済みと報告しない。** 実画像を確認できる環境では、確認した範囲と方法を報告に書く。

## 3. 動画生成プロンプト

動画生成モデルへ渡すプロンプト、脚本、絵コンテ、ナレーション・字幕・効果音の指定。

### 面と `surface`

`video_prompt`、`storyboard`、`narration`、`subtitle`、`sfx`、`final_frame` など。
`video_prompt`、`storyboard`、`visual` のいずれかが含まれれば、L2 は Visual leak 検査を適用する。音と最終フレームは見落としやすいため、面として分けて宣言することを推奨する。

### Clean Brief と生成

- 現在必要な**被写体、因果、動作、カメラ、編集、音、文字、最終フレーム**を定義する。時間軸を持つ媒体では、開始から最終フレームまでの各時点で何が見え、何が聞こえるかを肯定形で書く。
- **旧案の出来事を「起こらない出来事」として脚本へ残さない。** 「Xは倒れない」「Yは鳴らない」は、X・Y を演出上の前提として生成器へ戻す。
- 音の設計も現在状態から組む。警報、失敗音、旧案の台詞、旧案の BGM 指定を残さない。
- 最終フレームは受け手に最も長く残る面である。旧案の要素や不在の強調で終わらない。

### 検査で見る箇所

- 音だけに残る旧案: 警報、失敗音、旧案の台詞、ナレーションの言い換え。
- 字幕、テロップ、画面内テキストの指定。
- カット割り・編集指示に「Xが消える」「Xを外す」のような変更操作の記述が残っていないか（Rationale leak）。
- 最終フレームと余韻（フェードアウト中の音・文字）。

### 検査済みと報告できる範囲

- 検査済みと言えるのは**プロンプト・脚本の文面**だけである。
- **実動画を確認していない場合、フレームまたは音声上の残留を検査済みと報告しない。** 実動画を確認できる環境では、確認したフレーム範囲と音声の有無を報告に書く。

## 4. UI とラベル

画面上の文言、ボタン・メニューのラベル、プレースホルダー、空状態、エラー、ツールチップ、通知。

### 面と `surface`

`label`、`placeholder`、`empty_state`、`error`、`tooltip`、`notification`、`menu` など。
見出しにあたる画面タイトルやオンボーディングの冒頭は `headline`・`lead` として宣言すると、Attention leak の対象になる。

### Clean Brief と生成

- **非表示にした機能名を、空欄、無効（disabled）ラベル、プレースホルダー、グレーアウト項目として残さない。** 機能を外したなら、その導線ごと現在の情報設計で組み直す。
- 削除後の空白は、現在の機能に合う導線・説明・空状態の文言で埋める。「この機能は利用できません」で埋めない。
- **利用者へ必要なエラー、安全表示、状態説明は消さない。** 法令、安全、契約、アクセシビリティ上の必要表示は最優先である（§6.4）。却下要素と無関係な状態説明は漏れではない。

### 非発動対象

変更履歴画面、リリースノート、管理者向け監査画面、設定の差分表示は、旧案を記録に残すことが要件であり、本スキルの非発動対象として扱える（§6.3）。
利用者向けの通常画面と監査画面が同じリポジトリにある場合、manifest の `surface` に監査画面の面を含めないことで対象を分ける。

### 検査で見る箇所

- 空欄、無効ラベル、プレースホルダー、ツールチップ、aria-label、alt テキスト。文字として画面に出ないが読み上げられる面を見落としやすい。
- 設定項目名、メニュー項目、キーボードショートカットの説明、ヘルプ文。
- エラー文と空状態の文言が、却下要素の不在を主題にしていないか。

### 検査済みと報告できる範囲

- 検査済みと言えるのは L1・L2 へ渡した文言ファイル（ソース、リソースファイル、ローカライズ辞書）の内容である。
- **実行中の UI を確認していない場合、描画結果（切り詰め、フォールバック文言、動的に組み立てられる文字列）を検査済みと報告しない。**

### L1 の常駐（MAY）

UI 文言がリポジトリ内のファイルである場合、工程4a の L1 を単発実行に留めず、常駐させる選択肢がある（§13.3）。

- **linter のカスタムルール**: manifest の `literal_terms` を ESLint / textlint 等のカスタムルールへ写し、CI で `literal_terms` の再侵入を機械的に防ぐ。
- **Claude Code の PostToolUse hook**（matcher: `Write|Edit`）: 成果物ファイルへの書込み時点で `pink-elephant-scan --manifest <path> --draft <path>` を呼ぶ。hook 化した場合、L1 はモデルの判断を経由せず確実に適用される。

いずれも利用者が明示的に選んだ場合のみ導入する（§17）。終了コードは 0=PASS / 1=FAIL を判定とし、2〜5 は「判定なし」として扱う（§13.3）。常駐させるのは L1（字面）だけであり、L2 の意味検査は工程4b で都度実施する。
